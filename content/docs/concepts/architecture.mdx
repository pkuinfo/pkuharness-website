PKU Harness 从 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 借来了两个想法：
**一切皆插件**，以及 App **以 AI 为核心，但人和 AI 平等**。每项能力只实现一次，形式是一个有类型的工具（tool）。你点按钮时由界面调用它，聊天时由助手调用它。

## 分层 [#layers]

```
UI            routes · screens · design system (tokens, components, motion) · generative-UI catalog
                   │
Core runtime  plugin registry + permissions · agent loop · dashboard · scheduler · storage
              campus session manager (IAAA, per-service sessions)
                   │
Plugins       PLUGIN.md documents (interpreted)  ·  bundled TypeScript  ·  remote MCP  ·  providers
                   │
Native        campus-http module (redirect control, per-session cookie jars, HTTP/1.1, no proxy)
```

依赖只能向下。插件（plugin）从不引用 App 的代码，凡是插件自身以外的事，都要经过**宿主服务**（`ctx.services`）；界面则经过 **`HostUI`**。

## 框架本身 [#the-harness]

| 部分 | 是什么 | 面向插件的接口 |
| --- | --- | --- |
| **Agent 循环** | 用所有已启用的工具驱动模型流式输出（AI SDK，模型由任意服务商插件提供），支持多步调用（每次回复最多 10 步）。按会话保存模型可见的历史，压缩较早的轮次，并记录用量。 | `tools`、`instructions`、`context`、`contributes.commands` |
| **设计系统** | 设计令牌、原生控件和动效。插件界面基于它搭建，所以看起来是原生的，App 迭代后也不会坏。 | `HostUI`（`host.components`、`host.useTheme()`…） |
| **宿主服务** | 校园 HTTP、定时任务、小组件、待办、课表、通知就绪状态、文件、浏览器、加密、插件注册表。 | `HostServices`（`ctx.services`、`props.services`） |
| **生成式界面** | 一组组件目录，助手可以根据 JSON 描述在聊天和看板里渲染它们。 | `ui.render` 工具、`HostUI.components.GenUI` |

## 插件 [#plugins]

插件有三种形式：App 解释执行的 `PLUGIN.md` 文档、用 `definePlugin` 写的 TypeScript 对象（内置插件），或者一个 MCP 服务器（远程插件）。框架会把它们统一成同一种结构：一组 id 为 `<plugin>.<tool>` 的工具，各自带有效果（effect）和输入 schema，外加可选的界面。

```ts
import { definePlugin, defineTool } from '@pku-harness/sdk';
import { z } from 'zod';

export const helloPlugin = definePlugin({
  id: 'hello',
  name: '你好',
  description: '演示插件。',
  version: '0.1.0',
  scopes: [],
  tools: {
    greet: defineTool({
      title: '打招呼',
      description: 'Greet someone by name.',
      input: z.object({ name: z.string() }),
      effect: 'read',
      execute: async ({ name }) => ({ greeting: `你好，${name}` }),
    }),
  },
});
```

同一个插件写成文档，就是一个带 `tools: { greet: … }` 的 `PLUGIN.md`，工具用 YAML 步骤来写，见[声明式插件](/docs/build/declarative-plugins)。三种插件的对比见[插件](/docs/concepts/plugins)。

## 数据存在哪里 [#where-data-lives]

| 数据 | 位置 |
| --- | --- |
| 校园账号密码、模型 API key、远程插件 token | 设备密钥库（SecureStore） |
| 聊天会话、用量、小组件、定时任务、待办、课表、插件 KV | 设备上的 SQLite |
| 你主动开启的插件云端数据 | [PKU Harness Cloud](/docs/cloud) 服务商，端到端加密 |

默认情况下不经过任何项目服务器。你配置的模型服务商会收到对话内容，校园服务收到的请求和浏览器发出的一样。

## 代码如何到达用户 [#how-code-reaches-users]

| 改动内容 | 如何送达 |
| --- | --- |
| 插件文档（`PLUGIN.md`），包括随 App 内置的官方插件 | App 重新拉取它的链接（每天最多一次）；声明不变的直接生效，权限变宽的要等用户确认 |
| 远程（MCP）插件 | 服务器自己更新，App 实时调用 |
| 插件市场条目（`registry.json`） | App 实时拉取 |
| App 的 JavaScript、SDK、内置 TypeScript 插件 | 从我们自己的更新服务器下发签名的 OTA 更新（空中更新），下次启动时生效（或者发布新版 App） |
| 原生代码（模块、系统权限） | 发布新版 App |

OTA 更新基于 expo-updates，服务端是一个静态的、经过代码签名的服务器（`https://harness.novadiffusion.com/updates/`）。每次更新都由 CI 用只有维护者持有的密钥签名，App 内置证书，其他来源的更新一律拒绝。`runtimeVersion` 采用 fingerprint 策略，所以只要原生代码有改动，就需要新的 APK。插件文档完全不走 OTA，它们从各自的链接更新。
