PKU Harness borrows two ideas from [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness):
**everything is a plugin**, and the app is **AI-native but human-equal**. Each capability exists
once, as a typed tool. The UI calls it when you tap; the agent calls it during a conversation.

## Layers

```
UI            routes · screens · design system (tokens, components, motion) · generative-UI catalog
                   │
Core runtime  plugin registry + permissions · agent loop · dashboard · scheduler · storage
              campus session manager (IAAA, per-service sessions)
                   │
Plugins       PLUGIN.md documents (interpreted)  ·  bundled TypeScript  ·  remote MCP  ·  providers
                   │
Native        campus-http module (redirect control, per-session cookie jars, HTTP/1.1, no proxy)
```

Dependencies only point down. Plugins never import app code. Anything a plugin does outside itself
goes through **host services** (`ctx.services`), and UI goes through **`HostUI`**.

## The harness

| Part | What it is | Plugin-facing surface |
| --- | --- | --- |
| **Agent loop** | Streams a model (AI SDK, any provider plugin) with every enabled tool, multi-step (up to 10 steps per reply). Keeps a model-visible history per session, compacts old turns and records usage. | `tools`, `instructions`, `context`, `contributes.commands` |
| **Design system** | Tokens, native controls, motion. Plugin screens are built from it, so they look native and keep working as the app changes. | `HostUI` (`host.components`, `host.useTheme()`…) |
| **Host services** | Campus HTTP, scheduler, widgets, to-dos, timetable, notification readiness, files, browser, crypto, registry. | `HostServices` (`ctx.services`, `props.services`) |
| **Generative UI** | A catalog of components the agent can render from a JSON spec, in chat and on the dashboard. | `ui.render` tool, `HostUI.components.GenUI` |

## The four tabs

| Tab | Owner |
| --- | --- |
| Chat | The harness |
| Dashboard | A tab **slot** filled by the `dashboard` plugin (`contributes.tabs`) |
| Schedule | A tab slot filled by the `schedule` plugin |
| Settings | The harness (plus Settings rows contributed by plugins) |

## Plugins

A plugin is one of three things: a `PLUGIN.md` document the app interprets, a TypeScript object
built with `definePlugin` (bundled), or an MCP server (remote). The harness turns each of them into
the same shape: a set of tools with ids `<plugin>.<tool>`, effects and input schemas, plus optional UI.

```ts
import { definePlugin, defineTool } from '@pku-harness/sdk';
import { z } from 'zod';

export const helloPlugin = definePlugin({
  id: 'hello',
  name: '你好',
  description: '演示插件。',
  version: '0.1.0',
  scopes: [],
  tools: {
    greet: defineTool({
      title: '打招呼',
      description: 'Greet someone by name.',
      input: z.object({ name: z.string() }),
      effect: 'read',
      execute: async ({ name }) => ({ greeting: `你好，${name}` }),
    }),
  },
});
```

Written as a document, the same plugin is a `PLUGIN.md` with `tools: { greet: … }` and the tool
expressed as YAML steps; see [Declarative plugins](/en/docs/build/declarative-plugins).
[Plugins](/en/docs/concepts/plugins) compares the three kinds.

## Where data lives

| Data | Where |
| --- | --- |
| Campus credentials, model API keys, remote plugin tokens | Device keystore (SecureStore) |
| Chat sessions, usage, widgets, jobs, to-dos, timetable, plugin KV | SQLite on the device |
| Optional plugin data you opted into | A [PKU Harness Cloud](/en/docs/cloud) provider, end-to-end encrypted |

The default path has no project server. The model provider you configured receives the
conversation, and campus services receive the same requests a browser would send them.

## How code reaches users

| What changed | How it reaches users |
| --- | --- |
| A plugin document (`PLUGIN.md`), including the official ones bundled with the app | The app re-fetches its link (at most daily); same declarations apply, wider ones wait for the user |
| A remote (MCP) plugin | Its server updates; the app calls it live |
| A marketplace listing (`registry.json`) | Fetched live by the app |
| App JavaScript, SDK, bundled TypeScript plugins | A signed over-the-air update from our own update server, applied on the next launch (or a new app release) |
| Native code (modules, permissions) | New app release |

Over-the-air updates use expo-updates against a static, code-signed server
(`https://harness.novadiffusion.com/updates/`). CI signs every update with a key only maintainers
hold, and the app embeds the certificate and rejects anything else. `runtimeVersion` follows the
fingerprint policy, so any native change needs a new APK. Plugin documents don't use OTA at all;
they update from their own links.
