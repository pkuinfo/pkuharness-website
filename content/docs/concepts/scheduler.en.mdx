Anything time-based in PKU Harness is a **job** in one scheduler: a reminder, a to-do's reminder,
a class reminder, "check my card balance every morning". Users create jobs in the Schedule tab or by
asking the agent. Plugins create them with `services.scheduler`.

## Jobs

```ts
type Job = {
  id: string;
  title: string;
  trigger: Trigger;          // when
  action: Action;            // what
  enabled: boolean;
  source: 'user' | 'agent' | 'plugin';
  runs: number;              // occurrences fired (or passed)
  lastRunAt: number | null;
  nextRunAt: number | null;  // null when the series is over
  // check / agent jobs also keep lastValue, lastError, history (last 20 runs), failures …
  meta?: Record<string, unknown>;  // link back to the owner, e.g. { todoId }
  createdAt: number;
  updatedAt: number;
};
```

## Triggers

All times are **device-local**.

| Trigger | Fields | Covers |
| --- | --- | --- |
| `{ type: 'at' }` | `at` (epoch ms) | "in 2 days", "tomorrow 8:00" |
| `{ type: 'every' }` | `unit` (`minute` `hour` `day` `week`), `interval` (1–1000), `times?` (`"HH:MM"`, day/week), `weekdays?` (0 = Sunday … 6, week), `startAt`, `count?`, `until?` | "every morning at 8", "every 3 days, 16 times, then stop", "Mon/Wed/Fri 07:30 until the end of term" |

A series is a sequence of periods: one minute or hour step, one day, or one week starting Monday.
Each period has slots (times × weekdays). Slots before `startAt` are skipped. The rest are numbered
0, 1, 2… and cut off by `count`, `until` (inclusive), or both.

The agent and forms use a friendlier input, `ScheduleInput`, with local `"YYYY-MM-DD HH:mm"` strings:

```json
{ "type": "repeat", "unit": "day", "interval": 3, "times": ["09:00"], "count": 16 }
```

`toTrigger(input)` converts it. `summarize(trigger)` returns `{ schedule, next, total, finished }`,
for example `"每 3 天 09:00 · 共 16 次"` plus the next three times, so the agent can read the times
back to the user before saving.

## Actions

| Action | Fields | Runs |
| --- | --- | --- |
| `notify` | `title`, `body?`, `url?` (in-app route opened on tap) | Armed ahead of time as an exact notification; no code runs at fire time |
| `check` | `tool` (read-only, `<plugin>.<tool>`), `args?`, `condition`, `title`, `body?`, `url?` | Calls the tool, reads `condition.path`, notifies only if the condition holds; `{value}` in the text is replaced by the value |
| `agent` | `prompt` (4–1000 chars) | A fresh, read-only agent session with no chat history; replies `NO_REPLY` to stay silent, otherwise its short answer becomes the notification |

A condition is `{ path, op, value? }`, where `op` is one of `<` `<=` `>` `>=` `==` `!=` `changed` `always`.

```json
{
  "type": "check",
  "tool": "wallet.cardBalance",
  "condition": { "path": "balance", "op": "<", "value": 100 },
  "title": "校园卡余额只剩 ¥{value}，记得充值"
}
```

## Exact delivery (Android)

`notify` jobs are armed as exact alarms ahead of time, within a 14-day window and capped at 64 per
job and 400 in total. They are re-armed on start, on every change, when the app comes to the
foreground and from the background task.

`check` and `agent` jobs run in JavaScript. In the foreground a timer fires them on the minute.
When the app is in the background or killed, an exact alarm wakes a headless task. That task runs
whatever is due, arms the next alarm and removes the placeholder.

All of this needs the notification permission and the "Alarms & reminders" special access, which
Android 14+ denies by default. Battery optimisation is advisory. `services.notify.readiness()`
reports all three, `deliveryBlocker(readiness)` names the first blocker, and
`services.notify.fix(kind)` opens the matching system prompt or screen. Call `fix` from a tap.

## Unattended-run policy

Nobody is watching when a check runs, so it is limited, logged, and loud when it fails:

| Rule | Value |
| --- | --- |
| Tools a scheduled run may call | `read` only, re-checked at run time; an `ask` mode means declined |
| Enabled jobs | ≤ 50 (`MAX_ACTIVE_JOBS`) |
| Check frequency | at most every 15 min (`MIN_CHECK_GAP_MS`); no duplicate check (same tool, args, condition) |
| Agent jobs | ≤ 10 (`MAX_AGENT_JOBS`), at most hourly (`MIN_AGENT_GAP_MS`), ≤ 8 steps per run (`AGENT_MAX_STEPS`) |
| Late runs | A run more than 2 h late (`MAX_LATE_MS`) is logged as missed instead of alerting hours late |
| Run log | Last 20 runs (`HISTORY_LIMIT`): due vs actual time, result, value, error |
| Failures | 2 in a row (`FAIL_ALERT_AFTER`) tell the user once, again after 6 h; 10 (`DISABLE_AFTER`) turn the job off and say so |

## For plugin authors

- Write tools that are easy to check: `read`, fast, with a stable numeric or boolean field to
  compare (`balance`, `unread`, `available`). List them in `dataSources` so the agent can find them.
- Only create jobs with `services.scheduler.create({ …, source: 'plugin' })` in response to
  something the user did. Keep the job id (in `meta` or your `kv`) so you can update or remove the
  job later.
- The SDK exports the pure engine (`occurrencesAfter`, `nextOccurrence`, `describeTrigger`,
  `evaluate`, …). See [SDK → scheduler](/en/docs/sdk/scheduler).
