用户在首次引导时同意条款后，助手就可以代表用户操作已启用的插件（plugin）。每个插件对**每种效果（effect）各有一种授权方式**，用户可以在 设置 → 插件 → *某个插件* → AI 权限 里修改。

## 授权方式 [#modes]

| 授权方式 | 助手调用这类效果的工具时 |
| --- | --- |
| `auto` | 直接执行 |
| `ask` | 弹出审批提示（插件、工具、效果、输入），可选**允许**、**拒绝**和**始终允许** |
| `off` | 拒绝；助手会被告知这个工具已被禁用 |

## 默认值 [#defaults]

| 插件类型 | read | write | money | public |
| --- | --- | --- | --- | --- |
| 内置插件，未设 `defaultModes` | auto | auto | auto | auto |
| 内置插件，设了 `defaultModes` | 按声明，例如 `{ money: 'ask' }` | | | |
| 文档插件（`PLUGIN.md`），官方 | 按它的 `defaultModes`，否则 auto | | | |
| 文档插件，社区 | auto | ask | ask | ask（更严格的 `defaultModes` 优先） |
| 远程（MCP） | auto | ask | ask | ask |

用户可能想先确认的操作，就声明更严格的默认值：

```ts
definePlugin({
  // …
  defaultModes: { money: 'ask', public: 'ask' },
});
```

## 何时询问、问谁 [#who-is-asked-and-when]

决策只在一个地方做出，也就是宿主的 invoke 路径，按以下顺序：

1. 工具存在，且它所属的插件**可用**（能力需求已满足）并**已启用**。
2. `userOnly` 工具只有在 `actor === 'user'` 时才放行，否则拒绝。
3. 用工具的 zod schema 校验输入。
4. 授权方式为 `off` → 拒绝。
5. `actor === 'scheduler'` 且效果不是 `read` → 拒绝（无人值守时只能读取）。
6. 授权方式为 `ask` 且 `actor === 'scheduler'` → 视为拒绝（没有人可以问）。
7. 授权方式为 `ask` 且 `actor === 'agent'` → 弹出审批提示；用户拒绝 → 助手收到 “declined” 错误。
8. `actor === 'user'` 从不弹提示：点按钮本身就是用户的意图。

## 工具之外的授权 [#consent-beyond-tools]

| 内容 | 在哪里授权 |
| --- | --- |
| 校园服务 | 登录校园账号；插件声明 `scopes`（站点/服务）和 `requires: ['campus-session']`，这些会显示在插件页面上 |
| PKU Harness Cloud | 每个插件单独的**允许云端**开关，旁边列出插件用大白话写的 `disclosure` 说明；未授权的调用会抛出 `CloudError('consent_required')`（[云服务](/docs/cloud/plugin-guide#2-consent)） |
| 文件 | 只有用户能选文件（在页面里调用 `services.files.pick`，绝不能从助手的工具里调用） |
| 通知、精确闹钟 | 系统授权弹窗，在用户点击时通过 `services.notify.fix(kind)` 触发 |
| 读到不可信内容之后写入的记忆 | 先存为*待确认*，由用户在记忆页面批准 |

## 插件作者须知 [#rules-for-plugin-authors]

- **必须**如实声明每个工具的效果。`money` 和 `public` 存在的意义，就是让用户能把这类操作放在确认之后。
- **不得**在 `read` 工具里偷偷修改数据（比如“读取并标为已读”）。
- **应当**把 `money` 和 `public` 的 `defaultModes` 设为 `ask`，除非这个操作可以轻松撤销。
- **应当**把既读又写的工具拆成两个。
- **必须**用 `userOnly` 标记助手不能自己打开的“闸门”（例如批准它自己写的记忆）。
