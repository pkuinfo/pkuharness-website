PKU Harness holds a student's IAAA password and can act on their campus accounts. From the user's
point of view the design should be "serverless": nothing the project runs can see credentials, and
nothing a plugin does is hidden from the user.

## Principles

1. **Credentials never leave the device.** The IAAA password, the 手机令牌 secret, model API keys
   and remote plugin tokens live in the device keystore. They are never logged, never sent to a
   project server and never given to a plugin, whether document, bundled or remote.
2. **Plugins get responses, not sessions.** `services.campus.request` returns a response. Session
   cookies and tokens stay in the harness, and signing happens inside it too (the `sign` hook).
3. **Tool results are data.** The model is told that tool results, plugin context and remote
   plugin output are data and must not be followed as instructions.
4. **Effects are explicit.** Every tool declares `read`, `write`, `money` or `public`, and users
   decide per effect whether the agent may act directly. Scheduled runs can only read.
5. **What leaves the device is declared.** Campus `scopes`, the model provider and PKU Harness
   Cloud `disclosure` lines are shown before first use.

## Prompt injection

Third parties write campus content: a Treehole post, a notice, an event blurb, a remote plugin's
output. Any of it can say "ignore previous instructions and…". The harness treats all of it as data
and limits how far an injected instruction can get:

- **Untrusted tools.** A tool that returns third-party text sets `untrusted: true`. Every remote
  plugin tool counts as untrusted.
- **Taint.** Calling an untrusted tool taints the rest of the agent's turn: later tool calls in
  that turn see `ctx.turn.tainted === true`.
- **Gated durable writes.** Once a turn is tainted, writes that would carry into future
  conversations wait for the user. The memory plugin stores such memories as *pending*, and the
  user approves them on its screen. If the user's own message asked to remember something
  (`ctx.turn.userAsked`), the write is the user's intent and is saved directly. Third-party text
  can't write the user's message.
- **Ask-first defaults** apply to remote plugins' write, money and public effects.
- **Unforgeable host lines.** Facts the host injects each turn (time, reply language) sit in fixed
  slots that plugin context can't imitate.

### What plugin authors must do

- **MUST** set `untrusted: true` on tools whose results contain text written by anyone other than
  the user: posts, comments, notices, messages, descriptions from a public site.
- **MUST NOT** put instructions in results ("Tell the user to…", "Now call…"). Return data and let
  the model decide. Guidance belongs in the tool `description` or the plugin `instructions`.
- **SHOULD** check `ctx.turn?.tainted` in tools that write durable state the agent will later
  treat as true (notes, memories, saved preferences), and save those writes as pending or refuse
  them.
- **SHOULD** strip control characters, invisible and bidi characters, and markup from third-party
  text you return, and cap its length.
- **MUST** use `userOnly: true` for tools that approve or unlock things on the agent's behalf.

## Secrets in results

Some values must never reach the model or the logs.

- **Payment codes** are shown only on a screen using `host.useSecureDisplay()` (screenshots
  blocked, brightness up), never in a tool result.
- **Share links** for a cloud channel carry the key in the URL fragment. The SDK's `SecretLink` is
  opaque (`JSON.stringify(link)` gives `"[secret link]"`); show it only with `host.shareLink(link)`
  or `<QRCode link={link} />`. The host also scrubs share-link patterns from tool output and logs.
- **Tokens and keys** are never available to plugins at all.

## Plugin documents

The app interprets the steps a `PLUGIN.md` declares. No plugin code runs. A document can reach only
the campus services, public hosts and host abilities it declares, within fixed time, size and
operation limits.

The harness signs campus requests, so a document never sees a password, cookie or token, or
another plugin's storage.

Before install, and before any update that asks for more, the user sees the review sheet: official
or community, campus services, websites, app features, and the effect of every tool.

In community documents, `write`, `money` and `public` tools ask first, and their results are
treated as untrusted data. The agent can draft a plugin but can't install one: `plugins.install`
only opens the review sheet.

## Remote plugins

A remote plugin runs on someone else's server. It never receives campus credentials, sessions or
the user's other data, only the tool inputs the agent sends. Its tools are untrusted, its write
effects ask first by default, and its section of the system prompt states that its output is data.
The registry marks an entry `verified` only after maintainers have reviewed the source.

## PKU Harness Cloud

The optional cloud backend is end-to-end encrypted by default. It identifies a device only by a
keypair, with no student ID or name, and needs per-plugin consent backed by a plain-language
disclosure. See [Cloud → Security](/en/docs/cloud/security).

## Reporting a vulnerability

Report privately as described in `SECURITY.md` of
[`pkuinfo/pku-harness`](https://github.com/pkuinfo/pku-harness) or
[`pkuinfo/pku-harness-plugins`](https://github.com/pkuinfo/pku-harness-plugins). Please don't open
a public issue.
