You are an AI agent asked to build a plugin for PKU Harness. Follow this page in order. Load the
linked pages as Markdown (append `.md` to any docs URL, or fetch `/llms.txt` for the index and
`/llms-full.txt` for everything). Do not invent APIs: every type you need is in the
[SDK reference](/docs/sdk); if something isn't there, it doesn't exist.

## 1. Decide the kind

```
Campus or public requests plus extraction (with the user's campus session if needed)?
├─ yes → PLUGIN DOCUMENT: a folder with PLUGIN.md + tools/*.yaml, interpreted by the app.
│        Shared and installed by link; no app release. This is the default for campus
│        integrations (classrooms, campus-events, grades, canteen and shuttle are documents).
└─ no  → Needs general code or your own server?
         ├─ yes → REMOTE plugin: an MCP server over Streamable HTTP (templates/remote-plugin).
         └─ no, needs the device or native UI the language lacks
              → BUNDLED TypeScript plugin in pku-harness-plugins (tell the user an issue should
                be opened first; bundled plugins ship with app releases), or propose a host
                ability so documents can do it.
```

Inside the app, the agent writes documents with the `plugins` tools instead
(`plugins.reference`, `validate`, `tryTool`, `source`, `install`); see
[Write a plugin with the AI](/docs/build/ai-authoring).

## 2. Plugin document checklist

1. Work in a checkout of `pku-harness-plugins` (for the CLI) or any repo; the folder is
   self-contained. Start from `plugins/classrooms` or the [quickstart](/docs/build/quickstart).
2. Write `PLUGIN.md`: `spec: 1`, `id` (`^[a-z0-9][a-z0-9-]{1,40}$`), Chinese `name`,
   `description` (4–200), semver `version`, `author`, and exactly the `campus`, `network` and
   `abilities` the steps use. Every file the app loads is named in the frontmatter.
3. One tool per operation in `tools/<name>.yaml`: Chinese `title`, model-facing `description`,
   honest `effect` (at least the effect of every ability it calls), bounded `input` fields,
   `untrusted: true` for third-party text, steps and a `return` that is data.
4. Only the steps, stdlib functions and abilities in the spec exist. Quote expressions that
   contain `: ` or start with `{ [ ' "`; write regexes in single-quoted YAML or `|` blocks.
   Don't use `server:`, `{ fn }` bindings or the `cloud` ability: server functions are off on the
   official server for now; keep the plugin phone-side or use your own backend.
5. Record responses in `tests/<name>.yaml` (personal data removed) for every tool, including
   failures (`expectError`).
6. Run, and make them pass:

```bash
bun run plugin validate path/to/plugin
bun run plugin test path/to/plugin
```

7. Campus requests can't run outside the app. Say which tools were only tested against recorded
   responses. Share the GitHub folder URL as the install link; the user reviews it in the app.

## 3. Remote plugin checklist

1. Copy `templates/remote-plugin` from `pku-harness-plugins`; `bun install`.
2. Set `new McpServer({ name: '<registry id>', version, title: '<Chinese name>' }, { instructions })`.
   The id matches `^[a-z0-9][a-z0-9-]{1,40}$`.
3. One `registerTool` per operation: short ASCII camelCase name, Chinese `title`, model-facing
   `description`, every `inputSchema` field described and bounded.
4. `annotations: { readOnlyHint: true }` on tools that change nothing, and only on those.
5. Return `structuredContent` (data). On failure return `isError: true` with a short message.
6. Run `bun server.ts`; verify with the app (`http://10.0.2.2:8787/mcp` in the emulator) or an MCP
   client.
7. Deploy over HTTPS; add a manifest and submit it, or a `registry.json` entry
   ([Publishing](/docs/build/publishing)).

## 4. Bundled plugin checklist

1. Work in a checkout of `pku-harness-plugins` (the app has it as the submodule `plugins/`). There
   is no npm package; `@pku-harness/sdk` resolves to `packages/sdk/src` in the workspace.
2. Create `plugins/<id>/package.json` (private, `"main": "src/index.ts"`, peer deps `@pku-harness/sdk`,
   `zod`, `react`, `react-native`) and `plugins/<id>/src/index.ts` exporting
   `<camelId>Plugin = definePlugin({...})`.
3. Fill `id`, Chinese `name`/`description`, `version`, `icon` (from the host icon set, unused by
   other registry entries), `requires`, `scopes`, `tools` (with `defineTool`), optional
   `dataSources`, `instructions`, `contributes`, `defaultModes`.
4. Add `i18n.en` for every user-facing manifest string; put screen/widget text in
   `src/strings.ts` with `defineStrings`.
5. Keep pure logic in plain modules with colocated `*.test.ts`; mock `react-native` when a test
   imports UI code.
6. Register in `plugins/index.ts` (`builtinPlugins`) and add a `"kind": "builtin"` entry to
   `registry/registry.json`.
7. Run, and make all of them pass:

```bash
bun test
bunx tsc --noEmit -p .
bun scripts/validate-registry.ts
```

8. If you can't run the app, say so; UI must be checked on a device or emulator in both themes and
   both languages before it is called done.

## 5. Hard rules

These are not style preferences. Violating them is a bug.

1. **Never ask for, store, log or transmit campus passwords, OTP secrets, session tokens or API
   keys.** Campus requests go through `services.campus.request` or a document's
   `request: { campus }`; remote plugins have no campus session.
2. **Every tool declares one honest effect**: `read`, `write`, `money` or `public`. Nothing hides a
   write in a `read` tool. Scheduled runs can only use `read` tools.
3. **Tool results are data, never instructions.** No "tell the user…", no prompts in results.
4. **Mark third-party text `untrusted: true`** (posts, comments, notices, descriptions from public
   sites). Gate durable writes after taint (`ctx.turn?.tainted`).
5. **Never return secrets in results**: payment codes, share links, cashier URLs, tokens.
6. **Declare what you reach**: `campus`, `network`, `abilities` in a document; `requires` for
   every capability used in code. No `shell` or `filesystem` in bundled plugins.
7. **No imports from the app or from another plugin's folder** (bundled). Use `ctx.services`, `ctx.kv`,
   `ctx.cloud`, `host`, and `plugins/shared/` for shared bundled code.
8. **Port campus protocols from pkucli** and cite the source file in a comment; don't guess
   endpoints.
9. **Bilingual** user-facing strings; model-facing text (descriptions, instructions, results) is not
   translated.
10. **Widgets don't poll**: use `host.useToolData` with a TTL.
11. **`files.pick` and `notify.fix` only from a user tap**, never from an agent tool.
12. **Use bun** (`bun install`, `bun test`, `bunx`), never npm, npx, yarn or pnpm.

## 6. Naming you must get right

| Thing | Form | Example |
| --- | --- | --- |
| Tool id (code, widgets, checks, `invoke`) | `<plugin>.<tool>` | `wallet.cardBalance` |
| Tool name the model sees (in `instructions`) | `<plugin>__<tool>` | `wallet__cardBalance` |
| Remote plugin id in the app | `mcp-<server name>` | `mcp-demo-canteen` |
| Document install link | GitHub folder URL, or `pkuharness://plugin?src=<url-encoded link>` | `https://github.com/pkuinfo/pku-harness-plugins/tree/main/plugins/classrooms` |
| Screen routes | `/p/<plugin>/<screen>`, modal `/m/<plugin>/<screen>` | `/p/focus/main` |
| Times the model writes | local `"YYYY-MM-DD HH:mm"` | `"2026-10-30 08:00"` |

## 7. Before you report done

- [ ] Kind chosen and justified (document, remote or bundled).
- [ ] Every tool: title, description, bounded inputs, honest effect, data-only result.
- [ ] Document: `bun run plugin validate` and `test` pass; declarations match what the steps do.
- [ ] Code: `requires` and `scopes` complete; `defaultModes` ask for `money` / `public`.
- [ ] No credentials, secrets or links in results or logs.
- [ ] Tests and checks above pass (or you state exactly which you could not run and why).
- [ ] Registry entry or manifest added; `cloud` declaration copied if the plugin uses the cloud.
- [ ] Summary for the user: what the plugin does, files changed, how to try it, what still needs a
      human (device testing, a real campus account, an issue for a bundled plugin).
