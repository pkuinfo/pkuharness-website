## Device identity

On first use, each device generates two keypairs and keeps the secret keys in the keystore
(after first unlock, this device only):

| Key | Algorithm | Used for |
| --- | --- | --- |
| Signing key | Ed25519 | Signing token challenges |
| Box key | X25519 | Key agreement |

That is the whole identity: no student ID, no name, no phone number. Settings → Cloud shows a
fingerprint of the signing key, plus **reset identity** and **delete cloud data**
(`DELETE /v1/devices/me`, which the app also calls before a full reset).

## Registration: proof of work

`POST /v1/devices` costs a proof of work instead of an account. That makes farming identities
expensive without app attestation, which would break self-built APKs:

```
prefix = UTF-8("pku-harness-cloud/v1/pow\n" + salt + "\n" + signPub + "\n" + boxPub + "\n")
hash   = SHA-256(prefix ‖ UTF-8(nonce))         # nonce: decimal, no leading zeros, ≤ 15 digits
valid  = hash has ≥ difficulty leading zero bits
```

`salt` and `difficulty` come from `GET /v1/meta`, and the server accepts both its current and its
previous salt. The default difficulty of 16 takes about a second on a phone. Clients refuse
anything above 28, so a hostile provider can't make phones spin forever. Both public keys are part
of the prefix, so one solution registers exactly one identity.

## Plugin tokens

Every request carries a bearer token bound to **one device, one plugin and a set of services**,
valid for 10 minutes. The device gets it by signing a challenge with its Ed25519 key:

```
pku-harness-cloud/v1/auth
<aud>        provider origin, lowercase scheme://host[:port]
<deviceId>
<plugin>
<services>   deduplicated, sorted, joined by ","
<ts>         Unix ms
<nonce>      16 random bytes, base64url
```

A token for server functions adds one more line, `doc <hash> <link>`: the plugin document version
the user consented to.

- `aud` stops a provider from replaying a signature at another provider.
- The server accepts `|now − ts| ≤ 5 min` and rejects a nonce it has already seen in that window.
- Store namespaces and channel ownership come from the token (`sub`, `plg`), never from the path,
  so one plugin can't touch another plugin's data.
- Plugins never see tokens. The host mints them and attaches them to requests.

## Envelopes

Every encrypted payload, on the wire and at rest, is an envelope:

```json
{ "v": 1, "n": "<24-byte nonce, base64url>", "c": "<ciphertext ‖ 16-byte tag, base64url>" }
```

It uses XChaCha20-Poly1305 with a random 24-byte nonce, optionally with associated data (a
channel id, a frame kind) that whoever opens it must supply again. This is implemented once, in
`@pku-harness/cloud-protocol`, on the audited [noble](https://paulmillr.com/noble/) libraries
(pure JavaScript). The app (Hermes), the reference server (Bun) and viewer pages (WeChat webview,
no WebCrypto) all run that one implementation.

## Share links and channels

```
https://<provider>/s/<channelId>#k=<base64url 32 bytes>
```

- The secret `k` sits in the **URL fragment**, which browsers never send to the server.
- `authKey = HKDF-SHA256(k, "pku-harness-cloud/v1/join")`. The server stores only
  `joinHash = base64url(sha256(authKey))`, so it can check joins without being able to join.
- `encKey = HKDF-SHA256(k, "pku-harness-cloud/v1/enc")` never leaves the devices. It seals the
  channel `meta` and feeds into the per-peer key.
- To join, the viewer sends `authKey` and an ephemeral X25519 public key. Frames between owner and
  peer use `HKDF-SHA256(ikm = X25519(own, other) ‖ encKey, salt = chanPub ‖ peerPub, info = "pku-harness-cloud/v1/peer")`.
- **Claim**: `maxPeers` defaults to 1. The first joiner claims the channel and anyone after that
  gets `409 conflict`, so a forwarded link is useless. The owner can kick a peer to free the seat.
- Checks the server can't verify (a masked-name hint, a PIN) run on the owner's device. The
  server only rate-limits joins (20 per IP per minute) and locks a channel after 5 wrong
  `authKey`s.

### Keeping links away from the model

- The SDK's `SecretLink` is opaque: `JSON.stringify(link)` gives `"[secret link]"`.
- The host scrubs share-link patterns (`/s/<id>#k=…`, `pkuharness://share/<id>#k=…`) from tool
  output and logs (`scrubShareLinks`).
- Tools never return links. Screens show them with `host.shareLink` or `<QRCode link>`.

## Limits

Rate limits are token buckets per `(deviceId, plugin, service)` and per IP, reported in
`RateLimit-*` headers. A 429 becomes `CloudError('rate_limited', retryAfterS)`. Defaults:

| Resource | Default |
| --- | --- |
| Store | 1 MB and 1,000 keys per plugin per device, 64 KB per value |
| Channels | 5 open per device, TTL 60 s – 24 h (default 15 min), at most 5 peers, 4 KB frames, 60 frames/min, 64 mailbox slots |
| Joins | 20 per IP per minute |
| Push (planned) | 100 pending schedules |
| Functions (off on the official server) | 60 calls per minute |

## Residual risks

- **Metadata.** A provider sees timing, sizes and IP addresses. Disclosure lines have to say so.
- **Viewer pages run the provider's JavaScript.** A malicious operator could serve a page that
  leaks `k`, exposing what flows through that one channel during the share (but not credentials).
  Mitigations: pages are static, built reproducibly from the plugins repository and served with a
  strict CSP (`connect-src 'self'`). Viewers who have the app decrypt natively through a deep link
  and never run the provider's JavaScript.
- **Server functions** see plaintext by design. They must be declared in `PLUGIN.md`, disclosed
  and approved, and the server runs only the document version the user consented to. They are off
  on the official server for now.
